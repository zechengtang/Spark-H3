# 1004 下一批实验任务 Prompt

下面的 Prompt 供显卡资源空闲后执行；本文只是任务说明，**现在不要启动生成、解码或 VBench 作业**。任务范围是单侧 reblock、对侧复用布局下的 `M2 × distance` 消融；不继续做 `landmarks64`。

## Prompt 1：预检、复用与最小数值校验

> 在 `/mnt/CFS/tangzecheng/repos/Spark-H3` 准备下一批单侧 reblock 消融。先只做只读审计和必要的轻量验证，不要直接启动完整实验。保留已有实验目录和用户工作树改动。
>
> 1. 固定样本为 `../MiniMax-H3-Benchmark/vbench_core5_percent_subsets/10pct/samples.json` 中的 **25 个 prompt**，不是任意 25 个，也不是 50-prompt 集合的前 25 个。两个时长都用 `seed=42`、20 requested steps、现有 6-step warmup、768×1344、Top-K 0.1、同一模型/精度和现有 Dense 参考；5s 为 120 帧，10s 为 240 帧。不要采用 `samples.json` 内逐样本 seed。校验 sample ID、prompt SHA256、seed、配置和模型身份。
> 2. 冻结本批 attention 源码和脚本指纹，记录 git revision、dirty diff/source-tree SHA256、GPU UUID、协议和依赖版本。核对现有结果的 `latent_sha256`、完整性及来源；不要因文件存在就默认为可复用。
> 3. 预定复用以下 `M2=both + cosine + midpoint` 对照：5s `q_reuses_k_layout` 来自 `reblock_ablation_5s768p_25p_roll11_q_reuses_k_layout_20261002`，5s `k_reuses_q_layout` 来自 `reblock_ablation_5s768p_25p_roll15_priority4_20261003`；10s 两组均来自 `reblock_priority_10s768p_25p_20261003`。5s 的既有 Dense 和双侧 reblock baseline 可作外部参照，但**不是**单侧 2×2 的两个对照单元。
> 4. 5s Q 复用 K 的历史源码指纹与当前不同，先在当前冻结源码下重跑 **1 个预先指定的 5s 样本**（例如官方 10pct 列表中的第 1 个），配置必须完全等同旧 `both+cosine` Q 复用 K 记录。比对最终 latent 的 SHA256；若字节不一致，再做张量级误差、置换/尾部索引和配置排查。只有确认数值一致，或查明只是无关的序列化差异，才将旧 25 条结果直接视作本批质量对照。若确认计算结果改变，不要偷偷混用旧结果；报告原因并重跑受影响的 5s Q 对照 25 条。K 复用 Q 与 10s 两个对照也要核对源码/配置指纹；若发现实际计算路径变化，同样升级校验。
> 5. 检查 M2 切换时 exact tail 的原始 token 身份按同一复用方向的 `both+cosine` 参照保持固定；检查 Q/K 复用的置换方向和 V 跟随 K 的语义。用现有测试和小规模 smoke test 验证四种组合都真正进入预期分支，且没有退回默认配置。
> 6. 输出一份明确的可复用清单、新生成清单及实际任务量，并给出是否可以执行 Prompt 2 的结论。若预检失败，先修复或报告，不启动大批量作业。

历史记录位于 `/mnt/CFS/tangzecheng/experiments/` 下对应同名目录；5s/10s 原始 runner 分别见 `scripts/reblock_ablation_5s768p.py`、`scripts/reblock_priority_10s768p.py`。旧版与新版双侧 baseline 在同一 25 样本上的 latent SHA256 已有 **25/25 一致**的交叉验证，但这不能代替上述 Q 分支的直接校验。

## Prompt 2：资源空闲后执行 2×2 消融

> 在 Prompt 1 通过、显卡资源确认空闲后，实现并运行 **两个复用方向 × 两个时长 × M2 两档 × 距离两档** 的完整矩阵。按现有 runner 的可恢复协议创建新的实验目录，不覆盖旧结果；复用通过校验的既有 `both+cosine` 记录和 Dense/conditioning 参考。不要顺带添加 `landmarks64`、新 seed、50 prompts 或其他消融轴。
>
> 对每个 `(5s, 10s) × (q_reuses_k_layout, k_reuses_q_layout)`，四个单元分别是：`both+cosine`（已存在的主对照）、`both+euclidean`、`none+cosine`、`none+euclidean`。`both/none` 指 `landmark_tree_v2_m2_side`；M2 estimator 保持 `hilbert_midpoint`，`landmark_tree_v2_landmark_mode` 保持 `midpoint`，landmark 数 32，proxy 两轮、`farthest_pair` seed、`mean` update，初始 `flat` 顺序和其余 baseline 配置保持不变。两个复用方向分别运行，不合并为一个变体。
>
> 正常复用情况下，新生成量是 **12 个单元 × 25 prompts = 300 条候选 latent**，另加 Prompt 1 的 1 条校验运行；相应视频按后续质量/VBench 需求解码。若校验失败，按实际受影响单元增加，不无条件全量重跑。复用记录必须在本批 manifest 中按 `sample_id + prompt hash + seed + frames + arm config + latent hash + source` 追踪，不能仅凭 case 序号关联。每条记录保存生成状态、失败/重试、GPU、denoise 秒数、latent hash、配置和源码指纹。批次运行期间若源码发生变化，应暂停并区分批次，不把变化前后的结果无标记混合。
>
> 尽量沿用既有 8×A800 的 resume-safe 调度、CUDA 同步 denoise 计时、conditioning 缓存、Dense 参考、质量解码和 VBench 管线。先做每个新单元的少量 smoke，再运行完整 25 prompts；完成后确认 16 个单元各有 25/25 有效样本。不得仅凭已有 `m2_both_euclidean` 等**双侧**消融结果填充单侧单元。

## Prompt 3：质量、速度与交互分析

> 在 Prompt 2 完成后，用同一 Dense 参考、同一解码/指标实现，统计 25 prompts 全视频 PSNR、SSIM、LPIPS；若相关视频和评分资源齐备，按官方 10pct 对应样本统计五个 VBench 维度：subject consistency、background consistency、motion smoothness、imaging quality、aesthetic quality。不要把五维样本数当成每维 25；先核对维度到 sample ID 的映射。复用历史质量文件前校验指标协议与视频/latent 身份，缺失或不兼容的指标只补算必要部分。
>
> 对每个时长和复用方向分别报告四个单元的绝对结果，以及相对同方向 `both+cosine` 的逐 prompt 配对差值、均值、95% 置信区间和 win/draw/lose。预先声明 draw 阈值及其用途；不要用阈值代替置信区间或把“不显著”写成“等价”。再计算 `M2 × distance` 交互项，并比较两个复用方向的效应是否一致；双侧 reblock baseline 只作外部参照，不能替代单侧对照。
>
> 单列 denoise 时间的均值、中位数和逐 prompt 差值。历史批次和新批次的耗时受 GPU/批次影响；跨批次速度只作描述性比较。若需要精确判断本次 2×2 的速度代价，在同 GPU/同批条件下补跑最小数量的 `both+cosine` 计时对照，并说明额外成本。不要据微小的 Q/K 耗时差异推断实现层必然更快。
>
> 最终交付：完整的单元×时长结果表、逐 prompt CSV/JSON、质量/VBench/速度分析、可复用与新跑记录来源、失败与偏差说明、源码/协议指纹、以及是否值得继续某个方向的结论。只有当证据支持时才宣称性能提升或质量等价。
