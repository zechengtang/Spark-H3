# Spark 两种新分块方案：5s768p 实测

两种方案均已完成独立代码实现、正确性检查、同输入模块回放，以及各自一次同形状 4-evaluation 预热和两轮正式 8-evaluation 完整生成。正式结果采用最终代码及同一份 `libproducer_fast.so`。

## 实现与输入

- 方案 1 `feature_replay`：采样 Q 构造变换矩阵；分块生成 K 并仅保留视频段的变换特征表；聚类后释放该表，再分块投影完整 QKV，执行 BSA 与 reweight。没有同时保留完整原始 K。
- 方案 2 `resident_k`：保留完整、完成 norm/RoPE 的 K 和小变换矩阵；聚类按需暂存至多 64 MiB 的变换特征块，沿用原评分核；规划后从原始 K 生成量化 K，立即释放 BF16 K；后续分别投影 Q、V，producer 直接读取两者，不拼接 QV。没有完整变换 K 表，也没有 CPU K staging。
- 两条路径由 `comfyui_spark_split.py` 独立调度，不调用旧 Python `spark_attn_chunked`。复用 Sol 的量化/工作区格式以及 Spark route/exact/reweight 原生计算核；新增 CUDA producer 支持已归一化的 K 和独立 Q/V。
- 首次稀疏 evaluation 的 bootstrap 额外扫描 V 获取量化尺度，并分块求 K 的 FP32 均值；其余 250 次稀疏调用使用上一 evaluation 的量化统计参数。当前输入的路由与 reweight 仍逐次计算。
- RTX 3090，SM86，本机上报物理显存 49,152 MiB；ComfyUI 0.38.2、Python 3.12.3、Torch 2.12.1+cu130、Triton 3.7.1。模型文件、LoRA 和依赖沿用 `docs/chunktest30.md` 已建立的隔离环境，详见 `environment.json`。
- 1344×768、124 帧、24fps（5.1667 秒）、seed 42；8 evaluations，前 2 次 dense，后 6 次 sparse，共 50 层；Top-K 20%、query tail、q_reuse_k、joint-video、producer chunk 4096；同一 Turbo 8step LoRA 和提示词。每个 case 独立进程，单 GPU 串行执行。
- 启动参数统一为 `--reserve-vram 1.5 --cache-classic --disable-fast-disk --preview-method none`，保留默认动态权重加载。未模拟 24 GiB 显存。

## 完整推理

采样秒数采用采样节点 WebSocket 边界，与此前 runner 相同；workflow 时间包含本轮执行的解码与保存，正式轮复用模型/conditioning 节点缓存。进程显存按目标 PID 每 100 ms 采样，可能漏过更短尖峰。表中峰值取两轮最大值，原始逐轮数据保存在 case 的 `result.json`。

| 实现 | 采样秒数，两轮（中位） | workflow 秒数，两轮（中位） | 采样 / 全流程峰值 MiB |
|---|---:|---:|---:|
| 方案 1：变换 K + QKV 重算 | 175.741, 176.121 (**175.931**) | 214.158, 214.551 (**214.354**) | 45510 / 45510 |
| 方案 2：原始 K + 按需变换 + Q/V | 174.967, 175.053 (**175.010**) | 213.508, 213.771 (**213.639**) | 45374 / 45374 |

以下为 2026-10-30 同机同规格的历史参考；本轮没有重新执行它们的完整工作流。两轮时间样本不足以判定百分之几的差异具有统计显著性。

| 历史参考 | 采样中位秒数 | 进程峰值 MiB |
|---|---:|---:|
| spark_attn / r3 | 157.945 | 44342 |
| spark_attn_chunked / r3 | 174.607 | 45710 |
| sol_attn_chunked / r3 | 152.263 | 43944 |

方案 1：变换 K + QKV 重算相对历史旧 chunked：观测进程峰值减少 **200 MiB（0.44%）**；采样中位耗时变化 **+0.76%**。

方案 2：原始 K + 按需变换 + Q/V相对历史旧 chunked：观测进程峰值减少 **336 MiB（0.74%）**；采样中位耗时变化 **+0.23%**。

两种新方案的完整推理峰值仍高于历史普通 `spark_attn` 的 44,342 MiB。本轮结果证明规划阶段可以缩小，但未证明新 chunked 在完整推理中比普通 Spark 更省显存。

每轮均确认 8 evaluations、2 次 dense、300 次新路径调用（50 bootstrap / 250 steady），无意外回退；两种 native 计数名称表示同一调用链，不相加。实际投影次数也已检查：方案 1 有 3000 个完整 QKV chunk；方案 2 有 3000 对 Q/V chunk，正式阶段完整 QKV chunk 为 0。两者均有 2500 个 K chunk、500 个 bootstrap KV chunk，以及 300 组采样 Q。

全部正式 MP4 经 ffprobe 确认 1344×768、124 帧、24fps、一个音频流；video/audio latent 均保存。

## 同输入模块回放与峰值位置

使用此前真实 5s768p 捕获的 GPU 驻留 BF16 原始 QKV，T=38541、H=56、D=128、video_tokens=37296。计入 norm/RoPE、当前输入聚类、量化、重排、BSA/reweight 和输出分配，排除模型权重、线性投影、CPU 传输和 VAE。采样 Q 按需读取，Q/V 回放直接使用输入视图，不额外打包。每项预热 3 次后进行 20 次交错/反序 CUDA-event 测量并同步，每次释放上次输出后重置 allocator 峰值。旧 r3 在本轮重新回放。

| 模块 | 中位 ms | allocator 峰值增量 MiB |
|---|---:|---:|
| r3-steady | 129.56 | 1622.04 |
| r3-bootstrap | 136.93 | 1504.07 |
| feature_replay-steady | 122.17 | 1503.91 |
| feature_replay-bootstrap | 125.34 | 1503.94 |
| resident_k-steady | 125.71 | 1503.91 |
| resident_k-bootstrap | 128.77 | 1503.94 |

两个新方案的 steady 峰值均为约 **1504 MiB**，比本轮旧 r3 steady 的约 **1622 MiB** 少 **118 MiB（7.28%）**。与此前普通 Spark 模块约 3060 MiB 相比，新路径的模块峰值约减半；这不等于整个模型推理显存减半。

| 阶段 | 方案 1 | 方案 2 |
|---|---:|---:|
| 规划输入已就绪时的活跃增量 | 511.92 MiB | 528.85 MiB |
| 规划阶段累计峰值 | 696.29 MiB | 766.73 MiB |
| 全部 attention 的峰值 | 1503.91 MiB | 1503.91 MiB |

这验证了“一份全局 K/变换 K 加少量状态”的规划方式。最终峰值出现在 BSA/reweight：约 **916 MiB 工作区 + 527 MiB 输出 + 61 MiB 排列及其他辅助量**。方案 2 的原始 K 在 Q/V producer 前已释放。进一步压缩 reblock 不能直接突破这个后续峰值。完整推理还包含模型权重、动态加载和 allocator/图缓存，因此不能用规划输入的 1/3 比例推断进程峰值。

## 正确性

- 6 项测试通过：4 项覆盖 padding/非整块视频、bootstrap/steady、排列有效性与原生 carrier 输出一致性；2 项覆盖普通权重和 INT8 ConvRot 权重的独立 Q/V 投影及方法恢复。日志为 `tests.log`、`tests-projection.log`。
- 真实 INT8 模型预热中抽查 Q、K、KV、Q/V 子投影，均与完整 QKV 对应部分逐位一致。Q/V 检查只在预热首个相关调用执行。
- 同一真实输入下，两种新方案在 bootstrap 和 steady 的排列、输出、kmean、vscale 均逐位一致；steady 也与旧 r3 逐位一致。
- 新 bootstrap 与旧 r3 非逐位一致：分块 FP32 K 均值的求和顺序不同。捕获输入上，输出 max_abs=0.0625、mean_abs=6.77e-7；kmean max_abs=2.26e-6，vscale 逐位一致。该差异经过后续离散路由和多层多步计算可能放大，完整 latent 误差单独列出。

## 代码、复现与交付

- `comfyui_spark_split.py`：两个独立调度入口、K-only / Q/V-only 投影、native producer 调用和统计计数。
- `h3_sparse_attention/landmark_lazy_k.py`：原始 K 的按需变换聚类，临时特征上限 64 MiB。
- `native/spark_split/producer.cu`：独立 K 与 Q/V producer、单路 norm/RoPE。
- `scripts/build_spark_split.py`：对齐原 BSA 的 `--use_fast_math` 编译参数，输出 build manifest。
- `tests/test_spark_split.py`：上述 6 项测试。`comfyui_nodes.py` 增加环境变量选择新入口的分派。

```bash
python scripts/build_spark_split.py --kitchen /path/to/comfy-kitchen --output /path/to/libproducer_fast.so --arch 86
export H3_SPARK_SPLIT_LIBRARY=/path/to/libproducer_fast.so
export H3_SPARK_SPLIT_SCHEME=feature_replay  # 或 resident_k
# 使用 Spark 节点，use_chunked=true；其余参数按本报告固定设置。
```

独立测试工作区：`/root/autodl-tmp/spark-two-plans-5s768p-20261031/`。最终完整推理目录为 `results/feature_replay_final/` 与 `results/resident_k/`；runner、实际 graphs、日志、latent、视频、JSON 样本和来源哈希均保留。`source/MiniMax-H3/` 为已验收 r3 快照叠加新代码，未将工作区其他已有改动混入测试。

原始 `feature_replay/` 及 `resident_k_packed_qv_preliminary/` 是开发过程数据，不进入最终主表；前者在统一编译参数后复跑，后者在去除 QV 拼接时中止。早期直接融合变换与评分导致近似相等分数排序变化，最终使用有界特征块加原评分核消除该差异；producer 的量化舍入差异通过对齐编译参数消除。

共享盘归档：`artifacts/spark_split_5s768p_20261031/spark-two-plans-5s768p-sm86.tar.gz`，附同名 `.sha256`；包内含逐文件 `SHA256SUMS.json`。原始 QKV 捕获沿用上一轮归档，位置和哈希见 `capture_reference.json`。

本次只验证上述默认 q_reuse_k、BF16、head_dim=128、batch=1 的配置，新入口对不支持的配置显式报错。所列进程显存只代表本机上报 48 GiB 的 GPU 与当前动态加载策略。
